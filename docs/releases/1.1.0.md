# ZeroModel 1.1.0

ZeroModel 1.1.0 is the first release built around the complete package-based architecture and the new evidence-driven perception workflow.

This release moves ZeroModel beyond the original monolithic package into a ten-distribution workspace, adds a complete bounded perception and promotion lifecycle, introduces evidence-compiled visual contracts, strengthens provenance and rollback durability, and replaces stale release validation with an authoritative package-aware release gate.

## Highlights

### Ten-package architecture

ZeroModel is now distributed as ten coordinated Python packages:

* `zeromodel`
* `zeromodel-analysis`
* `zeromodel-observation`
* `zeromodel-vision`
* `zeromodel-perception`
* `zeromodel-video`
* `zeromodel-sqlalchemy`
* `zeromodel-artifacts`
* `zeromodel-trust`
* `zeromodel-navigation`

Each package owns a bounded namespace, declares explicit dependencies, and can be built, tested, installed, and validated independently.

The package topology is defined in `package-boundaries.toml`, which is now the authoritative source for:

* package identity;
* source roots;
* public namespaces;
* dependency relationships;
* publication eligibility;
* integration-test location;
* release version.

This replaces the previous single-package layout and removes the legacy root `zeromodel/` source tree.

## Evidence-compiled visual contracts

ZeroModel 1.1.0 introduces a compiler-driven method for turning visual benchmark requirements into explicit, inspectable evidence contracts.

The compiler supports:

* field-schema discovery;
* region and geometry inspection;
* candidate decoder selection;
* aggregation selection;
* representation sufficiency analysis;
* bounded candidate search;
* recovery of known visual relationships;
* negative results when the representation does not contain enough evidence.

The compiler does not silently invent evidence. When a visual requirement cannot be recovered from the available representation, it records the result as insufficient observability rather than claiming success.

The frozen Stage 4 evidence shows:

* 11 of 12 declared requirements compiled successfully;
* the unrecovered requirement was alien identity;
* the failure was attributed to insufficient observability in the available representation;
* all recoverable requirements matched the hand-authored reference behavior;
* known representation failures were rediscovered by the compiler rather than hidden.

This establishes a bounded compiler claim:

> Given an explicit benchmark schema, field representation, candidate decoder family, and evaluation policy, ZeroModel can search for and compile recoverable visual evidence contracts, while preserving explicit negative results for unsupported requirements.

It does not establish arbitrary scene understanding, open-world computer vision, or general visual reasoning.

## Visual transition evidence

The visual-transition benchmark now forms a required part of the release verdict.

The benchmark evaluates whether structured visual evidence can identify meaningful state changes more reliably than naive pixel comparison.

Validated results include:

* deterministic benchmark generation;
* component-aware visual evidence;
* transition-level field extraction;
* relation, component, value, and identity evaluation;
* comparison against pixel-difference baselines;
* bounded compiler recovery;
* preserved research and negative-result artifacts.

The visual-transition regression suite contains 125 tests and is now required by the release-candidate validator.

The suite is intentionally given a bounded 480-second timeout because measured runtime is approximately 3.5 to 4.2 minutes on the reference development machine.

## Durable activation and rollback

ZeroModel 1.1.0 adds database-backed activation and rollback for promoted perception models.

The SQLite reference implementation preserves:

* active model pointers;
* activation receipts;
* immutable rollback plans;
* rollback admissions;
* rollback receipts;
* execution-attempt events;
* ordered rollback operations;
* restart-safe state.

Rollback execution is allowed only when the current active state still matches the activated state named by the rollback plan.

Additional protections include:

* immutable rollback-plan identity;
* idempotent execution;
* exact inverse-operation storage;
* cross-instance SQLite coordination;
* corruption detection;
* schema-version validation;
* activation-receipt and rollback-plan identity checks;
* rejection of unsupported relaxed activation policy;
* explicit error translation at the service boundary.

This is a bounded in-process SQLite implementation.

It does not provide:

* distributed activation;
* multi-node consensus;
* arbitrary historical rewind;
* production authorization;
* semantic safety recovery;
* high-availability guarantees;
* production uptime or scale claims.

## Observation ledger and provenance

The observation architecture now supports immutable, database-backed records for materialized visual observations and their provenance.

The observation flow is:

```text
legacy deterministic generator
    ↓
MaterializedObservationDTO
    ├── ObservationDTO
    ├── MatrixBlobDTO
    ├── ProviderObservationDescriptorDTO
    └── ObservationOperationChainDTO
            ↓
ObservationLedgerService
            ↓
VideoActionSetStore
            ↓
InMemoryVideoActionSetStore
or
SqlAlchemyVideoActionSetStore
```

SQLite is used for:

* content-addressed matrix deduplication;
* relational ownership;
* immutable observation records;
* provider descriptors;
* ordered provenance chains;
* individual provenance operations;
* restart-safe retrieval.

DTOs are the only application objects allowed to cross store boundaries.

## Release validation

The release-candidate workflow has been rebuilt for the current package topology.

The validator now distinguishes:

* `passed`
* `failed`
* `missing`
* `zero_tests`
* `timed_out`
* `setup_failed`
* `skipped_optional`

Required test roots may no longer pass accidentally because a directory is missing or because pytest collects zero tests.

The authoritative integration-test root is now:

```text
tests/integration
```

The stale root:

```text
integration_tests/
```

has been retired from:

* local runners;
* GitHub Actions workflows;
* package tooling;
* editor configuration;
* release validation;
* package reports.

The release validator now covers:

* repository quality checks;
* bounded fast tests;
* package-local source tests;
* cross-package integration tests;
* visual-transition regression tests;
* wheel and source-distribution builds;
* Twine metadata checks;
* clean-environment wheel installation;
* public API imports;
* package topology consistency;
* release-report generation.

The ten-package topology, including `zeromodel-perception`, is now represented in:

* fast-test coverage;
* Ruff scope;
* public API manifests;
* release artifact reports;
* package-local test layers;
* wheel smoke tests.

## Minimal example

```python
from zeromodel import LayoutRecipe, ScoreTable, VPMPolicyLookup, build_vpm

score_table = ScoreTable(
    values=[
        [1.0, 0.0],
        [0.0, 1.0],
    ],
    row_ids=[
        "state:left",
        "state:right",
    ],
    metric_ids=[
        "LEFT",
        "RIGHT",
    ],
)

recipe = LayoutRecipe.from_dict(
    {
        "version": "vpm-layout/0",
        "name": "policy-source-order",
        "row_order": {
            "kind": "source",
            "tie_break": "row_id",
        },
        "column_order": {
            "kind": "source",
        },
        "normalization": {
            "kind": "per_metric_minmax",
            "clip": True,
        },
    }
)

artifact = build_vpm(score_table, recipe)

decision = VPMPolicyLookup(artifact).read("state:right")

assert decision.action == "RIGHT"
```

## Compatibility

ZeroModel 1.1.0 requires Python 3.10 or later.

The package metadata declares support for:

* Python 3.10
* Python 3.11
* Python 3.12

This release removes reliance on the old monolithic repository source layout.

Code that imported from supported public `zeromodel` namespaces should continue to use those public namespaces.

Code that relied on repository-internal paths, undeclared modules, editable-install leakage, or the deleted root package layout may require updating.

## Migration from 1.0.x

The most important change is the package split.

Previously, capabilities were collected inside one monolithic distribution.

In 1.1.0:

* core VPM functionality remains in `zeromodel`;
* analytical functionality is in `zeromodel-analysis`;
* observation contracts are in `zeromodel-observation`;
* visual functionality is in `zeromodel-vision`;
* evidence and promotion workflows are in `zeromodel-perception`;
* video-domain functionality is in `zeromodel-video`;
* SQLAlchemy persistence is in `zeromodel-sqlalchemy`;
* artifact functionality is in `zeromodel-artifacts`;
* trust functionality is in `zeromodel-trust`;
* navigation functionality is in `zeromodel-navigation`.

Install only the packages required by your application.

Internal package dependencies use exact ZeroModel release-version pins so the coordinated package family remains version-aligned.

## Claims boundary

A successful ZeroModel 1.1.0 release establishes that the named packages:

* build successfully;
* pass their declared release tests;
* install into a clean Python environment;
* expose the recorded public APIs;
* satisfy the declared package boundaries;
* preserve the bounded runtime and integration contracts exercised by the release gates.

This release does not establish:

* general artificial intelligence;
* open-world visual recognition;
* arbitrary image understanding;
* formal verification of all behavior;
* scientific validity of every experimental provider;
* universal transformation invariance;
* distributed rollback;
* production authorization;
* planet-scale performance;
* microcontroller performance without named hardware measurements;
* constant-time navigation over arbitrary stores;
* semantic correctness outside the tested domains.

`docs/claims-audit.md` remains the source of truth for public capability wording.

## Known limitations

* Identity recovery remains limited when the visual representation does not expose stable identity evidence.
* The evidence compiler searches a bounded candidate family rather than arbitrary programs.
* Visual-transition tests are deterministic but relatively slow.
* SQLite activation and rollback are reference implementations for bounded in-process use.
* Research results remain domain-specific and should not be generalized without additional evidence.
* Some historical code-quality exceptions remain recorded in the repository quality report.
* The package family must be released as a coordinated version set.
